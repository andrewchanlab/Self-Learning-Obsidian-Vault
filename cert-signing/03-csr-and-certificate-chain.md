# 憑證簽署請求（CSR）與憑證鏈 / CSR and Certificate Chain

## Learning Point 學習要點

當你向 CA 申請 TLS 憑證時，第一步是生成 CSR（憑證簽署請求）。理解 CSR 的結構與憑證鏈的運作，是掌握 PKI 的關鍵。

When applying for a TLS certificate from a CA, the first step is generating a CSR (Certificate Signing Request). Understanding CSR structure and certificate chain operation is key to mastering PKI.

---

## CSR（憑證簽署請求）/ Certificate Signing Request

### 什麼是 CSR？/ What is a CSR?

**CSR** 是一個編碼文字區塊，包含你的公鑰和你想被包含在憑證中的資訊，由你的伺服器生成並發送給 CA。CSR 不是憑證，而是「申請表」。

A **CSR** is an encoded text block containing your public key and information you want included in the certificate, generated by your server and sent to the CA. A CSR is not a certificate — it's the "application form."

### CSR 包含的資訊 / CSR Contents

| 欄位 Field | 範例 Example | 說明 Description |
|---|---|---|
| **Common Name (CN)** | `www.example.com` | 要保護的網域 / Domain to protect |
| **Organization (O)** | `Example Corp Ltd.` | 組織名稱（OV/EV 需要）/ Organization name (required for OV/EV) |
| **Organizational Unit (OU)** | `IT Department` | 組織部門 / Department within organization |
| **Locality (L)** | `Hong Kong` | 城市 / City |
| **State/Province (ST)** | `Kowloon` | 州或省份 / State or province |
| **Country (C)** | `HK` | 國家代碼（2 字元）/ 2-character country code |
| **Public Key** | `-----BEGIN PUBLIC KEY-----` | 你的公鑰 / Your public key |

### CSR 生成命令 / CSR Generation Commands

**OpenSSL（通用）/ OpenSSL (generic):**

```bash
# 生成私鑰（建議 2048-bit 以上）
# Generate private key (recommend 2048-bit or higher)
openssl genrsa -out private.key 2048

# 生成 CSR
# Generate CSR
openssl req -new -key private.key -out server.csr

# 互動式輸入各欄位
# Interactive field input
# Country Name: HK
# State: Kowloon
# Locality: Hong Kong
# Organization: Example Corp Ltd.
# OU: IT Department
# CN: www.example.com
```

**使用配置檔（非互動式）/ Using config file (non-interactive):**

```bash
openssl req -new -key private.key -out server.csr \
  -subj "/C=HK/ST=Kowloon/L=Hong Kong/O=Example Corp/OU=IT/CN=www.example.com"
```

### CSR 格式（解讀）/ CSR Format (Reading It)

CSR 使用 PEM 編碼（Base64），可使用 OpenSSL 查看內容：

CSRs use PEM encoding (Base64). You can view contents with OpenSSL:

```bash
openssl req -in server.csr -noout -text
```

輸出範例 / Sample output:

```
Certificate Request:
    Data:
        Version: 0 (0x0)
        Subject:
            countryName               = HK
            stateOrProvinceName       = Kowloon
            localityName               = Hong Kong
            organizationName          = Example Corp Ltd.
            organizationalUnitName    = IT Department
            commonName                = www.example.com
        Attributes:
            challengePassword        : （可選的挑戰密碼 / Optional challenge password）
        Public Key:
            Public-Key: (2048 bit)
            Modulus: 00:e4a5:f8:...
            Exponent: 65537 (0x10001)
    Signature Algorithm: sha256WithRSAEncryption
```

## 憑證格式 / Certificate Formats

### 常見格式對比 / Common Format Comparison

| 格式 Format | 副檔名 Extensions | 用途 Use Case | 能否包含私鑰 Contains Private Key? |
|---|---|---|---|
| **PEM** | `.pem`, `.crt`, `.cer` | Apache, Nginx, 通用 / Apache, Nginx, general | ❌ (單純憑證 / Certificate only) |
| **DER** | `.der`, `.cer` | Java, Windows / Java, Windows | ❌ |
| **PKCS#12** | `.pfx`, `.p12` | Windows, Tomcat | ✅（需要密碼保護 / Password-protected） |
| **PKCS#7** | `.p7b`, `.p7c` | Windows, Java KeyStore | ❌（可包含完整鏈 / Can contain full chain） |

### 格式轉換 / Format Conversion

```bash
# PEM → DER
openssl x509 -in cert.pem -outform DER -out cert.der

# DER → PEM
openssl x509 -inform DER -in cert.der -outform PEM -out cert.pem

# 將憑證 + 私鑰打包為 PFX/P12
# Bundle certificate + private key into PFX/P12
openssl pkcs12 -export \
  -in cert.pem \
  -inkey private.key \
  -out bundle.pfx
```

## 憑證鏈 / Certificate Chain

### 什麼是憑證鏈？/ What is a Certificate Chain?

憑證鏈是從伺服器憑證到 Root CA 的完整信任路徑，讓瀏覽器能夠驗證你的憑證是受信任的。

A certificate chain is the complete trust path from the server certificate to the Root CA, allowing browsers to verify your certificate is trusted.

### 鏈的組成 / Chain Components

```
伺服器憑證（Leaf/End-Entity Certificate）
server certificate (leaf/end-entity certificate)
        │
        │ 由 Intermediate CA 簽署
        │ Signed by Intermediate CA
        ▼
Intermediate Certificate（中繼憑證）
        │
        │ 由 Root CA 簽署
        │ Signed by Root CA
        ▼
Root Certificate（根憑證）
        │
        │ 已預先安裝在作業系統/瀏覽器信任庫
        │ Pre-installed in OS/browser trust store
        ▼
   [ 受信任 / TRUSTED ]
```

### 完整範例 / Complete Example

假設你的網站使用 `www.example.com` 憑證，由 DigiCert 簽發：

Let's say your website uses a `www.example.com` certificate issued by DigiCert:

```
1. www.example.com 憑證（Leaf）
   ├── 頒發給 / Issued to: www.example.com
   ├── 頒發者 / Issued by: DigiCert SHA2 Extended Validation Server CA
   ├── 包含公鑰 / Contains public key
   └── 由 DigiCert SHA2 EV CA 私鑰簽署 / Signed by DigiCert SHA2 EV CA private key

2. DigiCert SHA2 Extended Validation Server CA（中繼憑證）
   ├── 頒發給 / Issued to: DigiCert SHA2 Extended Validation Server CA
   ├── 頒發者 / Issued by: DigiCert Global Root CA
   └── 由 DigiCert Global Root CA 私鑰簽署 / Signed by DigiCert Global Root CA private key

3. DigiCert Global Root CA（Root）
   ├── 自我簽署 / Self-signed
   └── 預先安裝在各大作業系統 / Pre-installed in major OSes
      Windows, macOS, Linux, iOS, Android
```

### 為何需要完整鏈？/ Why Is the Full Chain Needed?

瀏覽器從 Root CA 向下驗證：

Browsers verify top-down from Root CA:

```
1. 瀏覽器找到 Root CA（在信任庫中）
   Browser finds Root CA (in trust store)

2. 使用 Root CA 公鑰驗證 Intermediate CA 憑證
   Use Root CA public key to verify Intermediate CA certificate

3. 使用 Intermediate CA 公鑰驗證伺服器憑證
   Use Intermediate CA public key to verify server certificate

4. 驗證網域是否匹配、憑證是否未過期/未撤銷
   Verify domain match, certificate not expired/revoked
```

**如果鏈不完整**：瀏覽器無法完成驗證，顯示「此憑證不受信任」警告。

**If chain is incomplete**: Browser cannot complete verification, showing "certificate not trusted" warning.

## 部署時常見問題 / Common Deployment Issues

### 問題 1：缺少 Intermediate 憑證 / Issue 1: Missing Intermediate Certificate

```bash
# 錯誤：瀏覽器只收到伺服器憑證
# Error: Browser only receives server certificate

# 正確：需要同時發送伺服器憑證 + 中繼憑證
# Correct: Need to send server cert + intermediate cert together
```

**Nginx 配置 / Nginx config:**
```nginx
server {
    listen 443 ssl;
    ssl_certificate     /path/to/server.crt;      # 伺服器憑證 + 中繼憑證
    ssl_certificate_key /path/to/private.key;     # 私鑰（絕對不能泄露！）
    
    # 不要這樣做：只放伺服器憑證
    # Don't do this: server certificate only
}
```

### 問題 2：鏈順序錯誤 / Issue 2: Incorrect Chain Order

```bash
# 正確的鏈順序（從 leaf 到 root）:
# Correct chain order (leaf to root):
# 1. server.crt（你的憑證）
# 2. intermediate.crt（中繼憑證）
# 3. root.crt（根憑證，通常不需要）

# 合併為一個檔案：
# Combine into one file:
cat server.crt intermediate.crt > full_chain.crt
```

### 問題 3：私鑰與憑證不匹配 / Issue 3: Private Key and Certificate Mismatch

```bash
# 驗證公鑰指紋是否匹配
# Verify public key fingerprints match
openssl x509 -noout -modulus -in server.crt | md5sum
openssl rsa -noout -modulus -in private.key | md5sum

# 兩個 MD5 輸出必須相同
# Both MD5 outputs must be identical
```

## 面試常見問題 / Common Interview Questions

**Q: CSR 包含私鑰嗎？**
A: 不，CSR 只包含公鑰和申請人資訊。私鑰永遠不應該離開你的伺服器。CA 收到 CSR 後，用 CSR 中的公鑰簽發憑證，然後把憑證發還給你。

**Q: Does a CSR contain the private key?**
A: No, a CSR only contains the public key and applicant information. The private key should never leave your server. When CA receives a CSR, it issues a certificate using the public key from the CSR, then sends the certificate back to you.

**Q: 為什麼瀏覽器需要 Intermediate CA？**
A: 因為 Root CA 不直接簽發終端憑證（這樣太危險）。所有終端憑證由 Intermediate CA 簽發。如果只有 Root CA，則每個網站都需要在瀏覽器中內置自己的憑證（不可行）。

**Q: Why do browsers need Intermediate CAs?**
A: Because Root CAs don't directly issue end-entity certificates (too dangerous). All end-entity certificates are issued by Intermediate CAs. Without Intermediate CAs, every website would need its own certificate built into browsers (impractical).

**Q: 憑證鏈不完整會怎樣？**
A: 瀏覽器無法建立信任路徑到 Root CA，會顯示「此憑證鏈不完整」或「不受信任的憑證」錯誤。用戶看到安全警告，很可能立即離開網站。

**Q: What happens if the certificate chain is incomplete?**
A: Browser cannot establish trust path to Root CA, displaying "incomplete certificate chain" or "untrusted certificate" error. Users see a security warning and likely leave the site immediately.
